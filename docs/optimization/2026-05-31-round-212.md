# 第 212 轮：submitFeedback 不再把 malformed cardId 写回新日志

## 审查证据

- `core/database/src/main/java/com/zzz/androidvocab/core/database/OfflineReviewRepository.kt`
  - `submitFeedback()` 会先通过 `readQueueItem(command.cardId, ...)` 读取并修复卡片。
  - 但 `preparePendingReviewLog()` 之前仍直接使用：
    - `id = logId(command.cardId, command.reviewedAt.toString())`
    - `cardId = command.cardId`
- `core/domain/src/main/java/com/zzz/androidvocab/core/domain/SubmitReviewFeedbackUseCase.kt`
  - use case 只是透传 `cardId` 到仓库层，没有在这里做 canonicalize。
- `core/common/src/main/java/com/zzz/androidvocab/core/common/Ids.kt`
  - `logId` 直接由 `cardId + reviewedAt` 生成稳定 id。

结论：即使仓库层已经能把 malformed cache / queue item 修回 canonical 卡片，只要外部仍以坏 `cardId` 调一次 `submitFeedback()`，新增 pending/final `ReviewLog` 仍会继续把坏 id 写回 `review_logs`，`logId` 也跟着被污染。

## 方案

- 方案 A：在 UI / use case 层禁止传入 malformed `cardId`
  - 优点：上层语义更干净
  - 缺点：不能覆盖仓库公开 API；也不能修复未来其它调用方
- 方案 B：在仓库层以 `currentItem.card.id` 作为新增日志的唯一来源
  - 优点：改动最小，直接守住数据边界；与 `readQueueItem()` / Today 队列刚完成的 canonicalize 保持一致
  - 缺点：不会主动清洗历史旧日志，只保证之后不再新增坏日志

采用方案 B。

## 修改

- 修改 `core/database/src/main/java/com/zzz/androidvocab/core/database/OfflineReviewRepository.kt`
  - `preparePendingReviewLog()` 改为使用 `currentItem.card.id`
  - 新写入的 `ReviewLog.cardId` 与 `logId(...)` 都统一基于 canonical card id
- 修改 `core/database/src/test/java/com/zzz/androidvocab/core/database/OfflineReviewRepositoryTest.kt`
  - 新增 `submitFeedbackCanonicalizesNewLogWhenRequestUsesMalformedCachedCardId()`
  - 断言：
    - 仓库收到 malformed cached card id 后仍可正常提交
    - 新写入日志的 `cardId` 是 canonical
    - 新写入日志的 `id` 也是 `logId(canonicalCardId, reviewedAt)`
    - 数据库中不会新增新的 malformed `review_log`
