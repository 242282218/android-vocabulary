# 第 104 轮：ReviewLog 同时间戳稳定排序

## 审查证据

- `ReviewDao.getLogs(cardId)` 原来按 `reviewedAt ASC` 排序。
- `ReviewDao.getLogsForMissingCacheCards()` 原来按 `cardId ASC, reviewedAt ASC` 排序。
- `ExportDao.reviewLogs()` 原来按 `reviewedAt ASC` 排序。
- 正常提交路径用 `cardId + reviewedAt` 生成 log id，可拦截同卡同时间重复提交；但历史、手工或异常数据中仍可能存在同一 `reviewedAt` 的多条日志。
- replay、修复和导出都应在同时间戳下保持可重复顺序。

## 方案

- 方案 A：只记录风险。零改动，但 replay 顺序仍依赖数据库同值排序细节。
- 方案 B：只修 `getLogs`。能保护单卡 replay，但缺少 cache 修复和导出稳定性。
- 方案 C：`getLogs`、`getLogsForMissingCacheCards`、`reviewLogs` 都增加 `id ASC` tie-breaker，并补 DAO 回归测试。

采用方案 C。

## 修改

- `core/database/src/main/java/com/zzz/androidvocab/core/database/ReviewDao.kt`
  - `getLogs` 改为 `ORDER BY reviewedAt ASC, id ASC`。
  - `getLogsForMissingCacheCards` 改为 `ORDER BY cardId ASC, reviewedAt ASC, id ASC`。
- `core/database/src/main/java/com/zzz/androidvocab/core/database/ExportDao.kt`
  - `reviewLogs` 改为 `ORDER BY reviewedAt ASC, id ASC`。
- `core/database/src/test/java/com/zzz/androidvocab/core/database/ReviewDaoQueueTest.kt`
  - 新增 `reviewLogsUseIdTieBreakerForSameReviewedAt`，覆盖同一 `reviewedAt` 下 `getLogs`、missing-cache logs 和 export logs 的稳定顺序。
