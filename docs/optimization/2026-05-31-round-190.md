# 第 190 轮：压缩 Stats 页小屏密度，避免首屏指标和进度摘要横向挤压

## 审查证据

- `D:\PROJECT_ZZZZZZZZZ\设计美学研究\packages\mobile-design-knowledge\rules\small-screen-layout.md`
  - 要求小屏主内容跟随设备，不要把桌面式横向结构硬压进手机。
- `D:\PROJECT_ZZZZZZZZZ\设计美学研究\packages\design-core\principles\composition-and-hierarchy.md`
  - 要求移动端保持明确视觉路径，避免所有区域同时争抢注意力。
- `feature/stats/src/main/java/com/zzz/androidvocab/feature/stats/StatsRoute.kt`
  - `StatsSnapshotCard` 在同一行放 3 个 `MetricBlock`。
  - `BookProgressRow` 底部用一整行摘要文本串联“已学 / 待复习 / 掌握”。
- `app/src/androidTest/java/com/zzz/androidvocab/ScreenLayoutSmokeTest.kt`
  - 已覆盖 360x800 / 390x844 / 412x915 / 768x1024 视口，但 `Stats` 页 smoke 还停留在旧的 scope 文案断言，没有锁定新布局的窄屏可见性。

结论：`Stats` 页当前最明显的小屏风险不是数据，而是横向密度。尤其是 360dp 宽度下，连续学习卡片首屏三列指标会过挤，词书进度单行摘要也会把阅读路径拉平。

## 方案

- 方案 A：保持现有结构，只减小字体或缩短文案。
  - 优点：改动小。
  - 缺点：本质还是把横向结构硬塞进窄屏，压缩后信息层级反而更弱。
- 方案 B：只在 `Stats` 页页面层做小屏重排。
  - 连续学习卡片在窄屏下改成纵向指标堆叠。
  - 词书进度摘要从长句改成短标签组。
  - 优点：不改 design system 通用组件，影响面最小；符合小屏“单屏一个主要决策”的规则。
  - 缺点：需要同步 smoke test 断言。

采用方案 B。

## 修改

- `feature/stats/src/main/java/com/zzz/androidvocab/feature/stats/StatsRoute.kt`
  - `StatsSnapshotCard` 新增 `BoxWithConstraints`。
  - 当宽度小于 `380.dp` 时，3 个 `MetricBlock` 从单行改成纵向堆叠；更宽设备继续保留原三列布局。
  - `BookProgressRow` 底部从单行摘要改成 `FlowRow + TinyLegend`，分别显示：
    - 已学 `x/y`
    - 待复习 `n`
    - 掌握 `n`
- `app/src/androidTest/java/com/zzz/androidvocab/ScreenLayoutSmokeTest.kt`
  - `Stats` 页基础 smoke 改成断言新的全部词书 scope 文案。
  - 新增 `statsScreenKeepsCompactMetricsVisibleOnNarrowViewport()`，锁定窄屏下：
    - `年内最长`
    - `年内活跃`
    - `30天 P50`
    - `已学 620/3846`
    - `待复习 30`
    - `掌握 240`
    这些关键文本都还可见。
