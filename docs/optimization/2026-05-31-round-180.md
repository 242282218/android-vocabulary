# 第 180 轮：把时间线异常缓存重建写入结构化修复结果

## 审查证据

- `core/model/src/main/java/com/zzz/androidvocab/core/model/ReviewModels.kt`
  - `ReviewDataRepairResult` 之前只有 `before`、`after`、`repairedCount`。
  - 设置页若想提示“本次只是把时间线异常卡片的缓存重建回来，事实日志仍冲突”，只能依赖 `after.timelineConflictCardCount` 事后猜测。
- `core/database/src/main/java/com/zzz/androidvocab/core/database/OfflineReviewRepository.kt`
  - `repairReviewDataCacheInTransaction()` 实际会对完整快照但时间线异常的卡片重建 `ReviewCard` 缓存。
  - 但这个动作之前没有结构化返回值，调用方无法判断“这次 repair 到底有没有重建过这类卡片缓存”。

结论：仓库层已经知道“时间线异常卡片缓存被重建”这一事实，应由仓库层显式返回，而不是让 UI 用 `after` 报告推断。

## 方案

- 方案 A：保持现状，继续让设置页根据 `after.timelineConflictCardCount` 推断。
  - 优点：零模型改动。
  - 缺点：语义不准，无法区分“本次真的重建过”与“只是修复后仍存在人工问题”。
- 方案 B：给 `ReviewDataRepairResult` 新增 `timelineConflictCacheRebuiltCount`。
  - 优点：仓库层返回事实，UI 文案和后续导出都能基于真实结果。
  - 缺点：要同步少量测试构造。

采用方案 B。

## 修改

- `core/model/src/main/java/com/zzz/androidvocab/core/model/ReviewModels.kt`
  - `ReviewDataRepairResult` 新增 `timelineConflictCacheRebuiltCount: Int = 0`。
- `core/database/src/main/java/com/zzz/androidvocab/core/database/OfflineReviewRepository.kt`
  - `repairReviewDataCacheInTransaction()` 改为返回结构化 `RepairCacheResult`。
  - 当卡片缓存需要 `upsert`，且该卡片存在快照时间线异常时，累加 `timelineConflictCacheRebuiltCount`。
  - `daily_stats` 缓存重建仍只计入总 `repairedCount`，不混入该字段。
- `feature/settings/src/main/java/com/zzz/androidvocab/feature/settings/SettingsViewModel.kt`
  - 修复成功文案改为只根据 `timelineConflictCacheRebuiltCount` 追加特别说明。
  - 不再根据 `after.timelineConflictCardCount` 猜测本次是否真的重建过这类缓存。

## 测试

- `core/database/src/test/java/com/zzz/androidvocab/core/database/OfflineReviewRepositoryTest.kt`
  - 补断言：时间线异常卡片在 repair 后会返回 `timelineConflictCacheRebuiltCount = 1`。
- `feature/settings/src/test/java/com/zzz/androidvocab/feature/settings/SettingsViewModelTest.kt`
  - 更新原有时间线异常修复文案断言。
  - 新增用例：`after.timelineConflictCardCount > 0` 但 `timelineConflictCacheRebuiltCount = 0` 时，不应再误报“本次仅重建缓存”。
