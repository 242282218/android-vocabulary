# 第 121 轮：复习提交链路回滚证据复核

## 审查证据

- `core/database/src/main/java/com/zzz/androidvocab/core/database/OfflineReviewRepository.kt`
  - `submitFeedback()` 在 Room transaction 内读取当前卡片、计算 FSRS、构造 `ReviewLog`、写入日志、更新 `ReviewCard`、刷新 `DailyStats`。
  - `ReviewLog` 当前包含 `scheduledDaysAfter`、`difficultyAfter`、`stabilityAfter`、`retrievabilityAfter`、`stateAfter`、`dueAtAfter` 等调度后快照字段。
- `core/database/src/test/java/com/zzz/androidvocab/core/database/OfflineReviewRepositoryTest.kt`
  - 已覆盖重复日志主键冲突回滚卡片和统计。
  - 已覆盖 scheduler 失败不写入日志、卡片和统计。
  - 已覆盖卡片写入失败回滚日志和统计。

## 方案

- 方案 A：强行调整为“先插入日志，再计算 FSRS”。这会要求插入半成品日志或事后更新日志，和当前不可变日志模型冲突，迁移与修复成本高。
- 方案 B：保持当前事务模型，把“完整调度快照日志”作为持久化边界；用测试确认任何失败都不留下部分写入。范围小，符合现有 schema 和修复逻辑。
- 方案 C：拆出原始反馈事件表，再由调度器派生日志和卡片。模型更严格，但属于数据结构重构，需要迁移、导出、统计和修复链路一起改，本轮不做。

采用方案 B。本轮不改代码，只确认现有回滚测试仍通过，并记录设计取舍。
