# 2026-05-18 持续优化第 5 轮

## 当前状态判断

第 4 轮后，提醒权限与统计缓存重建已经补齐。继续审查统计事实来源时，发现今日新学数仍通过 `review_cards.firstReviewedAt` 识别，而统计缓存重建和导出已经转向 `review_logs` 派生口径。

## 对标项目可借鉴点

- SRS 产品的学习历史应以不可变日志作为事实来源，卡片表只是当前状态快照。
- 离线优先应用应尽量保证 UI 统计、导出统计、缓存统计的口径一致，避免恢复/迁移后出现数字不一致。

## 差距清单

### P1

- 今日新学数依赖 `review_cards` 快照。影响 Today 首页统计、每日新词上限计算和缓存刷新；根因是 SQL 用 `review_cards.firstReviewedAt = review_logs.reviewedAt` 判断新词；建议改为每张卡在 `review_logs` 中的最早复习记录；收益是卡片状态可重建或损坏时，统计仍可由日志复算；风险低。

### P2

- UI 还没有展示“统计已从日志重建”的维护动作入口。

### P3

- 可以后续把导出 JSON 加上统计口径版本，便于迁移审计。

## 本轮要做的优化项

1. 将 `StatsDao.observeDailyNewCount` 和 `dailyNewCount` 改为从 `review_logs` 首次记录派生。
2. 在数据库测试中加入“只有 ReviewLog、没有 ReviewCard 也能算出新学数”的回归断言。

## 具体修改方案

- `core/database/src/main/java/com/zzz/androidvocab/core/database/StatsDao.kt`
  - 两个每日新学数查询改为 `WITH first_reviews AS (...)`。
  - 使用每个 `cardId` 的最早 `reviewedAt` 作为新学判断。
- `core/database/src/test/java/com/zzz/androidvocab/core/database/DailyStatsCacheRebuildTest.kt`
  - 在只插入 `review_logs` 的场景下断言 `dailyNewCount` 和 `observeDailyNewCount` 都返回 1。

## 本轮风险

- SQL 增加一个按 `cardId` 聚合的 CTE。`review_logs` 已有 `cardId, reviewedAt` 索引，当前本地规模风险低。
- 如果未来允许手动导入历史日志且时间戳重复，需要再用日志 id 做稳定 tie-breaker；当前复习日志 id 已由 cardId 和 reviewedAt 生成，重复时间本身会冲突。

## 下一轮建议

1. 给提醒权限拒绝后的设置页增加明确反馈，让用户知道提醒已关闭是因为系统权限未授权。
2. 增强 UI instrumentation：覆盖深色模式、长释义、权限拒绝回退、360dp 下反馈按钮可点击。
3. 增加 release 构建与签名说明，补齐“可部署/可发布”文档链路。
