# 2026-05-19 持续优化第 23 轮

## 当前状态判断

Settings 已能控制每日提醒，MainActivity 会根据设置与通知权限调度或取消 WorkManager，worker 会在权限存在时发送通知。继续检查提醒链路后发现，核心决策逻辑散落在 MainActivity 的 `LaunchedEffect` 中：启用、权限存在、权限缺失、取消这几种状态没有独立单元测试。提醒是留存关键路径，不应只依赖 Compose 入口编译通过。

## 对标项目可借鉴点

- 成熟 Android 项目会把权限/调度决策从 Activity 中抽成可测试的纯逻辑，Activity 只负责调用系统 API。
- WorkManager 调度属于边界层，是否 schedule/cancel/request permission 应有稳定策略测试。
- 通知权限从 Android 13 开始变成运行时权限，权限状态变化必须和提醒开关保持一致。

参考：

- https://developer.android.com/develop/ui/views/notifications/notification-permission
- https://developer.android.com/topic/libraries/architecture/workmanager

## 差距清单（按 P0/P1/P2/P3）

### P0

- 暂无新增 P0。提醒基础链路存在，权限缺失时不会直接崩溃。

### P1

- 提醒调度决策缺少单元测试。影响范围是提醒启用、权限请求、取消调度；根因是决策逻辑直接写在 MainActivity；建议抽成纯函数并测试；收益是防止后续权限/设置改动破坏提醒；风险低。

### P2

- 真机上仍未执行 WorkManager connected test 和通知点击验证。影响范围是系统级调度、通知展示、点击打开 App；当前本机无在线设备。

### P3

- 后续可考虑用 OneTimeWork 自调度减少周期任务漂移，但 MVP 阶段 WorkManager 周期提醒已经足够。

## 本轮要做的优化项

1. 抽出提醒同步决策纯函数。
2. MainActivity 改为使用该决策结果执行 schedule/request/cancel。
3. 补单元测试覆盖三种状态：
   - 关闭提醒 -> cancel。
   - 开启且有权限 -> schedule。
   - 开启但无权限 -> request permission。

## 具体修改方案

- `app/src/main/java/com/zzz/androidvocab/NotificationPermission.kt`
  - 新增 `ReminderSyncAction`。
  - 新增 `reminderSyncAction(reminderEnabled, hasNotificationPermission)`。

- `app/src/main/java/com/zzz/androidvocab/MainActivity.kt`
  - `LaunchedEffect` 内不再直接嵌套判断，改为 `when (reminderSyncAction(...))`。
  - `Schedule`：调度每日提醒。
  - `RequestPermission`：取消现有 work 并请求通知权限。
  - `Cancel`：取消每日提醒。

- `app/src/test/java/com/zzz/androidvocab/NotificationPermissionTest.kt`
  - 新增三条 reminder sync 决策测试。

## 本轮风险

- 这轮只验证了提醒调度决策，不验证系统通知实际弹出。
- 如果用户在系统设置里撤销通知权限，worker 会静默成功但不弹通知；Settings 已能提示权限缺失，但仍需要真机回归。
- WorkManager 周期任务不是精确闹钟，实际触发时间可能被系统延后。

## 下一轮建议

1. 有设备时执行 `.\scripts\test\verify-device.ps1 -DeviceSerial <serial> -SkipBundleSmoke`，覆盖 WorkManager instrumentation test。
2. 增加通知点击 intent 的 instrumentation test，验证通知能打开主 Activity。
3. 若后续要求更准时提醒，再评估 OneTimeWork 自调度或 AlarmManager；MVP 暂不引入更高权限和复杂度。
