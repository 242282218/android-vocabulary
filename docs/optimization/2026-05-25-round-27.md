# 2026-05-25 持续优化第 27 轮

## 当前审查范围

本轮继续审查 Room 查询口径，重点是 `ReviewLog` 作为事实源后，统计、导出和队列排序是否都排除已失去词书归属的孤儿日志。该类日志可能来自词库重建、词书成员关系变更或修复流程，不能影响用户可学习队列。

## 对照原则

- 参考 Now in Android / Android Architecture Samples 的做法：数据层查询应把业务不变量收敛在 DAO 或 View 内，避免每个调用方重复过滤。
- 参考 FSRS 类项目的调度边界：队列优先级可以使用历史反馈，但历史反馈必须对应当前仍有效的词书归属。

## 发现

`ReviewDao.observeDueQueue()` 的困难度排序子查询直接读取 `review_logs`。在存在孤儿日志时，一个无效日志可以复用某个仍有效卡片的 `cardId`，从而抬高该卡片的困难度排序。统计和导出已使用 `valid_review_logs`，队列排序口径不一致。

## 方案取舍

1. 在 `observeDueQueue()` 子查询中改用 `valid_review_logs`。改动最小，和统计/导出口径一致，推荐采用。
2. 在每个读 `review_logs` 的查询里手写 membership join。过滤条件显式，但重复 SQL 多，后续容易改漏。
3. 在写入日志时禁止任何孤儿日志。能减少脏数据，但不能覆盖历史数据、词库成员关系变化和修复流程后的残留数据。

本轮采用方案 1，并增加 DAO 级回归测试覆盖该排序口径。
