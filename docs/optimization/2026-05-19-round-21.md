# 2026-05-19 持续优化第 21 轮

## 当前状态判断

第 19-20 轮已经让 `ReviewCard` 缓存缺失时可由 `ReviewLog` 自动恢复，并修正了 Today 队列把有日志卡片当作新词的问题。继续审查后发现，项目仍缺少全库级别的数据一致性审计：只能在访问单张卡或 Today 队列时触发修复，无法主动知道当前数据库里有多少缺失缓存、多少缓存与最后日志快照不一致、多少旧日志缺少完整快照。

## 对标项目可借鉴点

- 成熟 SRS 项目把复习历史作为事实来源，当前卡片表是可重建缓存；维护工具应能扫描并重建派生状态。
- FSRS/Anki 类调度依赖历史反馈演进状态，批量修复必须区分“有完整快照的新日志”和“legacy 日志”，避免用当前算法盲目改写旧历史状态。
- 离线优先 App 的维护能力应优先做成可重复、可测试的仓储能力，再考虑 UI 暴露。

## 差距清单（按 P0/P1/P2/P3）

### P0

- 暂无新增 P0。核心队列和单卡读取已能从日志修复缓存缺失。

### P1

- 缺少全库 ReviewLog/ReviewCard 一致性审计。影响范围是数据维护、迁移后验证和异常恢复；根因是只有单卡 replay，没有全库扫描入口；建议新增仓储级 inspect/repair API；收益是能主动发现并修复派生缓存问题；风险中等，涉及核心仓储。
- 批量修复不能盲目处理 legacy 日志。影响范围是算法升级后的历史正确性；根因是旧日志没有 `stateAfter` / `dueAtAfter`；建议完整快照日志可批量修复，legacy 只报告；收益是避免当前 scheduler 改变后重写旧状态；风险低。

### P2

- 审计结果目前还未接 UI。影响范围是普通用户和测试机手动修复；下一轮可接 Settings 的低频维护入口。

### P3

- 后续可增加内部日志或导出审计报告，但第一阶段收益不如 UI 入口。

## 本轮要做的优化项

1. 增加审计模型：报告有日志卡片数、缺失缓存数、不一致缓存数、legacy 日志卡片数。
2. `ReviewRepository` 增加 inspect/repair API，并补 domain use case。
3. `OfflineReviewRepository` 实现全库扫描和保守修复。
4. 补测试覆盖缺失缓存、不一致缓存、legacy 日志和修复行为。

## 本轮风险

- 批量修复入口当前只在代码层可用，尚未接 UI。
- legacy 日志仍可能需要单卡访问时 fallback scheduler 保障可用性；批量修复不处理它们是为了避免算法升级后的历史误写。
- 全库扫描会遍历所有有日志卡片，应作为低频维护能力，不应在每次页面刷新时执行。
