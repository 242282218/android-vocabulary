# 第 213 轮：完整性报告显式暴露历史 malformed ReviewLog.cardId

## 审查证据

- `core/model/src/main/java/com/zzz/androidvocab/core/model/ReviewModels.kt`
  - `ReviewDataIntegrityReport` 之前只把 `legacyLogCardCount`、`orphanLogCount`、`timelineConflictCardCount` 计入手工问题。
- `core/database/src/main/java/com/zzz/androidvocab/core/database/OfflineReviewRepository.kt`
  - `inspectReviewDataIntegrityInTransaction()` 已经能按逻辑卡片聚合日志，但不会把 `ReviewLog.cardId != canonical card|book|word` 当成问题。
- `core/database/src/main/java/com/zzz/androidvocab/core/database/AndroidExportRepository.kt`
  - 导出的 `dataIntegrity` 只序列化现有报告字段。

结论：前几轮已经做到“后续不再新增坏日志”，但历史 malformed `ReviewLog.cardId` 仍然既不会被 repair 改掉，也不会在 integrity/export 里被显式标记。导出看起来像“数据正常”，但实际仍含历史污染。

## 方案

- 方案 A：只在导出 JSON 层额外扫描 malformed `cardId`
  - 优点：改动最小
  - 缺点：仓库层 `inspectReviewDataIntegrity()` 和导出结果语义分叉
- 方案 B：在 `ReviewDataIntegrityReport` 正式增加 `malformedLogCardCount`，导出只做序列化
  - 优点：仓库层、导出层、测试语义一致；符合“历史日志不可变，但必须明确报问题”
  - 缺点：要补模型和测试

采用方案 B。

## 修改

- 修改 `core/model/src/main/java/com/zzz/androidvocab/core/model/ReviewModels.kt`
  - 新增 `malformedLogCardCount`
  - `manualReviewIssueCount` 现在包含这类历史污染
- 修改 `core/database/src/main/java/com/zzz/androidvocab/core/database/OfflineReviewRepository.kt`
  - `inspectReviewDataIntegrityInTransaction()` 统计每个逻辑卡片中是否存在 raw malformed `ReviewLog.cardId`
- 修改 `core/database/src/main/java/com/zzz/androidvocab/core/database/AndroidExportRepository.kt`
  - `dataIntegrity` JSON 新增 `malformedLogCardCount`
- 修改 `core/database/src/test/java/com/zzz/androidvocab/core/database/OfflineReviewRepositoryTest.kt`
  - 更新 malformed log 场景断言，证明：
    - repair 只能修缓存/统计
    - 历史 malformed log 仍作为 manual issue 保留
- 修改 `core/database/src/test/java/com/zzz/androidvocab/core/database/AndroidExportRepositoryTest.kt`
  - 新增 fake repository 导出字段断言
  - 新增 real repository 导出断言，证明导出既保留原始坏日志事实，也显式报告 `malformedLogCardCount`
