# 第 163 轮：Settings 数据维护失败时保留诊断证据

## 审查证据

- `feature/settings/src/main/java/com/zzz/androidvocab/feature/settings/SettingsViewModel.kt`
  - `inspectLearningData()` 和 `repairLearningData()` 失败时直接构造新的 `DataMaintenanceUiState(errorMessage=...)`。
  - 这会把之前成功检查得到的 `report` 和 `message` 一起清空。
- `feature/settings/src/main/java/com/zzz/androidvocab/feature/settings/SettingsRoute.kt`
  - “修复学习数据缓存”按钮只在 `dataMaintenance.hasRepairableIssues` 为 `true` 时显示。
  - 一旦失败把 `report` 清空，修复按钮也会消失，用户只能重新检查。
- `feature/settings/src/test/java/com/zzz/androidvocab/feature/settings/SettingsViewModelTest.kt`
  - 原测试覆盖了单次成功、单次失败、错误后再次检查，但没有覆盖“已有诊断结果后再次失败”这个状态机边界。

结论：当用户先检查出可修复问题，再执行修复或再次检查失败时，UI 会丢失上一次诊断证据，这不利于处理混合坏数据，也让失败恢复路径变差。

## 方案

- 方案 A：失败时继续重置整个 `DataMaintenanceUiState`。
  - 优点：实现最简单。
  - 缺点：旧诊断结果丢失，修复按钮和问题规模说明一起消失。
- 方案 B：失败时保留已有 `report` 和 `message`，只更新 `errorMessage` 与 `inProgress`。
  - 优点：保留上一次有效检查结果，失败只影响当前动作，不抹掉诊断证据。
  - 缺点：UI 会同时看到“旧结果 + 新失败提示”，需要接受这是有意的状态表达。

采用方案 B。

## 修改

- `feature/settings/src/main/java/com/zzz/androidvocab/feature/settings/SettingsViewModel.kt`
  - `inspectLearningData()` 失败时改为 `copy(inProgress = false, errorMessage = ...)`，不再重建整个状态。
  - `repairLearningData()` 失败时同样保留已有 `report/message`，只更新失败提示。
- `feature/settings/src/test/java/com/zzz/androidvocab/feature/settings/SettingsViewModelTest.kt`
  - 新增 `repairLearningDataFailureKeepsPreviousReportAndMessage()`。
  - 新增 `inspectLearningDataFailureKeepsPreviousReport()`。
  - 两个用例都显式收集 `uiState`，匹配 `SharingStarted.WhileSubscribed` 的真实行为。
