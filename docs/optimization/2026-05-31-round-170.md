# 第 170 轮：前台恢复不应重置当天提醒排程

## 审查证据

- `app/src/main/java/com/zzz/androidvocab/MainActivity.kt`
  - `LifecycleEventEffect(Lifecycle.Event.ON_RESUME)` 里在权限仍然已授予时会直接调用 `reminderScheduler.scheduleDailyReminder(...)`。
  - 同文件的 `LaunchedEffect(settings.reminderEnabled, reminderHour, reminderMinute, hasNotificationPermission)` 也会在提醒启用且权限存在时调用同一个 `scheduleDailyReminder(...)`。
- `worker/src/main/java/com/zzz/androidvocab/worker/ReminderScheduler.kt`
  - `scheduleDailyReminder()` 使用 `ExistingPeriodicWorkPolicy.UPDATE`。
  - `nextDailyReminderDelay()` 在当前时间晚于提醒时刻后会把首个触发时间推到明天。

结论：用户每次回到前台都会重排唯一 periodic work；如果当天提醒时间已过但旧 work 还没实际执行，这次 `UPDATE` 会把待执行提醒推到明天，导致今天提醒被跳过。

## 方案

- 方案 A：保留 `ON_RESUME` 内的重新排程。
  - 优点：前台恢复时看起来“更主动”。
  - 缺点：会重置已有 Work 的首触发时间，直接破坏当天提醒交付。
- 方案 B：`ON_RESUME` 只刷新权限状态，把 `schedule/cancel/request` 收敛到 `LaunchedEffect` 这一条状态驱动路径。
  - 优点：权限变更仍能在恢复时被感知，同时避免无意义重排已有 Work。
  - 缺点：没有为“前台恢复但状态完全未变”的场景再做一次冗余兜底。

采用方案 B。

## 修改

- `app/src/main/java/com/zzz/androidvocab/MainActivity.kt`
  - 删除 `ON_RESUME` 中的直接 `scheduleDailyReminder(...)` 调用。
  - 保留权限刷新，让 `hasNotificationPermission` 的变化继续驱动后续 `LaunchedEffect` 做统一同步。
  - 增加英文注释，说明这样做是为了避免把已待执行的当天提醒推迟到明天。
