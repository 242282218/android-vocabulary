# 第 207 轮：补齐 pending/legacy 完整性语义的导出证据

## 审查证据

- `core/database/src/test/java/com/zzz/androidvocab/core/database/OfflineReviewRepositoryTest.kt`
  - 上一轮已新增 `inspectAndRepairKeepPendingLogsAsManualIssues()`
  - 现已证明 pending 风格日志在仓库层会被归类为：
    - `missingCacheCount = 1`
    - `legacyLogCardCount = 1`
    - `manualReviewIssueCount = 1`
    - `repairableIssueCount = 0`
- `core/database/src/test/java/com/zzz/androidvocab/core/database/AndroidExportRepositoryTest.kt`
  - 已覆盖 `orphanLogCount`、`dailyStats`、`timelineConflictCardCount`
  - 缺口是没有证明导出层会原样保留这组“missing 但不可自动修复”的 pending/legacy 语义
- `core/database/src/main/java/com/zzz/androidvocab/core/database/AndroidExportRepository.kt`
  - `ReviewDataIntegrityReport.toJson()` 直接序列化字段
  - 风险点是后续有人可能误以为 `repairableIssueCount` 应该从 `missingCacheCount` 重新推导，导致导出误报

## 方案

- 方案 A：在 `AndroidExportRepositoryTest` 用 fake `ReviewRepository.report` 直接构造 pending/legacy 语义
  - 优点：改动最小，只验证导出契约，稳定
  - 缺点：不覆盖真实仓库计算链路
- 方案 B：在导出测试里插真实 pending 风格日志，再调用完整性检查后导出
  - 优点：链路更完整
  - 缺点：和上一轮仓库测试重复，测试更脆

采用方案 A。

## 修改

- 修改 `core/database/src/test/java/com/zzz/androidvocab/core/database/AndroidExportRepositoryTest.kt`
  - 新增 `exportUserDataKeepsPendingLogIntegrityClassification()`
  - 构造：
    - `missingCacheCount = 1`
    - `legacyLogCardCount = 1`
    - `repairableIssueCount = 0`
  - 断言导出 JSON 中：
    - `status = "issues"`
    - `missingCacheCount = 1`
    - `legacyLogCardCount = 1`
    - `repairableIssueCount = 0`
    - `manualReviewIssueCount = 1`
    - `issueCount = 1`

## 验证

运行：

```powershell
. .\scripts\lib\android-env.ps1
Use-AndroidVocabularyJavaHome
.\gradlew.bat --no-daemon --console=plain :core:database:testDebugUnitTest --tests "com.zzz.androidvocab.core.database.AndroidExportRepositoryTest" --tests "com.zzz.androidvocab.core.database.OfflineReviewRepositoryTest"
```

结果：通过。

结论：pending/legacy 日志在仓库层的“manual issue、不可自动修复”归类，已经被导出层测试明确钉住，不会在 JSON 序列化时被错误重算成 repairable issue。
