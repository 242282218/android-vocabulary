# 2026-05-19 持续优化第 18 轮

## 当前状态判断

项目已进入可离线使用的 Android 原生 MVP 形态：Kotlin + Jetpack Compose + Room + DataStore + WorkManager + FSRS，已覆盖 publish-safe 词库、ReviewLog 事实来源、复习队列、统计、导出、提醒和 release/AAB 构建脚本。

第 17 轮把 `assembleDebugAndroidTest` 加入本地与 CI 质量门，但 connected tests、AAB 设备拆包安装、首屏 smoke 仍需要真机或模拟器。继续检查刚新增的 `verify-device.ps1` 后，发现诊断步骤里把 `adb devices -l` 写成了 `adb -s <serial> devices -l`。`devices` 是查询 adb server 的命令，不应绑定单个设备 serial；这个问题会导致设备验收脚本在日志采集阶段不稳定。

## 对标项目可借鉴点

- Android 官方测试文档建议通过 Gradle 的 `connectedAndroidTest` 在设备上运行 instrumentation tests，适合覆盖 Room migration、Compose smoke 和真实系统权限路径。
- Android 官方 bundletool 文档建议在 AAB 构建后用 `build-apks` / `install-apks` 本地复现应用商店生成和部署 APK 的行为；本项目的 AAB smoke 应保持这条链路。
- adb 官方文档把设备发现定义为 `adb devices -l`，多设备后再用 `adb -s <serial> ...` 指定目标命令；设备验收脚本应按这个边界拆分发现与执行。
- 成熟 Android 项目的设备验收通常会保留设备列表、系统属性、Gradle 输出和 logcat，便于失败后复现，而不是只给一句失败状态。

参考：

- https://developer.android.com/studio/test/command-line
- https://developer.android.com/tools/bundletool
- https://developer.android.com/tools/adb

## 差距清单（按 P0/P1/P2/P3）

### P0

- 暂无新增 P0。本轮本地验证通过，未发现影响已有核心功能正确性的回归。

### P1

- 设备验收脚本的 adb 诊断命令不规范。影响范围是测试机/真机验收的日志归档；根因是混淆了 adb 设备发现命令和设备定向命令；建议 `adb devices -l` 用于全局设备列表，`adb -s <serial> shell getprop` 用于目标设备属性；预期收益是设备验收脚本在单设备、多设备场景下行为一致；改动风险低。
- 设备验收使用方式在文档里仍偏粗。影响范围是后续只想跑 connected tests 或只想跑 AAB smoke 时容易重复耗时构建；根因是 README 和 release 文档只给完整命令；建议补充 `-SkipBundleSmoke`、`-SkipConnectedTests`、`-SkipBundleBuild`、`-BundlePath` 的组合示例；预期收益是测试机执行更可重复；改动风险低。

### P2

- 当前机器没有在线设备，无法实际执行 `connectedDebugAndroidTest` 和 AAB 安装 smoke。影响范围是真机 UI、权限、安装和导入路径；根因是本地环境缺设备；建议在测试机或本地模拟器补跑 `verify-device.ps1 -DeviceSerial <serial>`。

### P3

- 后续可把设备验收日志目录归档到 CI artifact 或发布验收记录，提升问题追踪能力。

## 本轮风险

- 这轮只修复了设备验收脚本的入口和诊断可靠性，没有证明设备端测试本身通过。
- `-ResetAppData` 仍会清理目标设备上的 App 本地学习数据，发布验收前必须明确是否使用该参数。
- `-AllowUnsignedBundle` / `-AllowDebugSigning` 只能代表本地链路验证，不能替代正式 release signing 验收。
