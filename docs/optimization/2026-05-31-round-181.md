# 第 181 轮：固定数据修复事务内的时间基准

## 审查证据

- `core/database/src/main/java/com/zzz/androidvocab/core/database/OfflineReviewRepository.kt`
  - `repairReviewDataCache()` 在同一个 `database.withTransaction { ... }` 里分别对：
    - `inspectReviewDataIntegrityInTransaction(...)`
    - `repairReviewDataCacheInTransaction(...)`
    - 再次 `inspectReviewDataIntegrityInTransaction(...)`
  - 之前每一步都单独调用 `clockProvider.now()`。
- `core/database/src/test/java/com/zzz/androidvocab/core/database/OfflineReviewRepositoryTest.kt`
  - 现有测试覆盖了缺卡修复、日统计缓存修复、时间线异常等结果，
  - 但没有锁定“同一轮 repair 的 before / repair / after 必须基于同一个 now”。

结论：如果修复事务恰好跨分钟、跨天或跨 DST 边界，修复前报告、修复逻辑和修复后报告可能基于不同时间点执行，结果会出现不必要的漂移。这属于数据维护链路的时间一致性问题。

## 方案

- 方案 A：只在 `repairReviewDataCache()` 入口捕获一次 `now`，整轮事务复用。
  - 优点：改动最小，直接修掉当前根因。
  - 缺点：只覆盖这条修复事务路径。
- 方案 B：把仓库内部所有 helper 都改成禁止再读时钟，统一由入口显式传 `now`。
  - 优点：约束更强。
  - 缺点：改动面更大，这轮不值得。

采用方案 A。

## 修改

- `core/database/src/main/java/com/zzz/androidvocab/core/database/OfflineReviewRepository.kt`
  - `repairReviewDataCache()` 现在先读取一次 `val now = clockProvider.now()`。
  - `before` 检查、缓存修复和 `after` 检查全部复用同一个 `now`。
- `core/database/src/test/java/com/zzz/androidvocab/core/database/OfflineReviewRepositoryTestSupport.kt`
  - 新增 `CountingClock`，用于统计仓库层实际读取 `now()` 的次数。
- `core/database/src/test/java/com/zzz/androidvocab/core/database/OfflineReviewRepositoryTest.kt`
  - 新增 `repairReviewDataCacheUsesSingleTransactionNow()`，锁定：
    - 同一轮 repair 只读取一次时钟
    - 即使整轮跑完 `before -> repair -> after` 也不允许重复取 `now`
