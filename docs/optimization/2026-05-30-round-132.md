# 第 132 轮：FSRS 调度耗时溢出防护

## 审查证据

- 时间入口扫描只发现 `SystemClockProvider` 使用 `Instant.now()` 和 `ZoneId.systemDefault()`，没有在业务层散落系统时间调用。
- `core/scheduler/src/main/java/com/zzz/androidvocab/core/scheduler/FsrsKotlinReviewScheduler.kt` 将 `ScheduleInput.durationMs: Long` 直接 `toInt()` 后再 `coerceAtLeast(0)`。
- 极长耗时会在 Long 到 Int 窄化时溢出为负数，再被夹到 0，导致传给 FSRS 的答题耗时证据失真。耗时来自 UI 计时，设备挂起、系统时间跳变或异常输入都可能放大该风险。

## 方案

- 方案 A：在 FSRS 调度边界把 `Long` 安全夹到 `[0, Int.MAX_VALUE]` 后再转 `Int`，并补单元测试锁住边界行为。范围小，不改日志模型和仓库接口。
- 方案 B：把全链路 `durationMs` 改成 `Int`。类型更贴近 FSRS SDK，但会触及日志模型、导出、统计和迁移语义，发布准备阶段风险过大。

采用方案 A。

## 修改

- `core/scheduler/src/main/java/com/zzz/androidvocab/core/scheduler/FsrsKotlinReviewScheduler.kt`
  - 新增 `Long.toFsrsDurationMs()`，先夹取再转 `Int`。
  - `reviewCard(...)` 调用改用该安全转换。
- `core/scheduler/src/test/java/com/zzz/androidvocab/core/scheduler/FsrsKotlinReviewSchedulerTest.kt`
  - 新增 `durationMsIsClampedBeforeFsrsIntConversion`，覆盖负数和 `Long.MAX_VALUE`。
