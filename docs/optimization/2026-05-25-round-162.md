# 2026-05-25 持续优化第 162 轮

## 当前审查范围

本轮接着第 161 轮，审查 release readiness 失败信息的机器可读性。当前 `failureMessage` 会把所有失败 requirement 拼成长行，便于保留原文，但不适合脚本快速判断失败范围。

## 发现

外部脚本如果只想知道哪些 requirement 失败，需要解析 `failureMessage` 长行中的 `name=failed|...` 片段。这个格式适合人看，不适合作为稳定接口。

## 方案

- 方案 A：只保留 `failureMessage`。无改动，但脚本解析脆弱。
- 方案 B：保留 `failureMessage`，额外写入 `failedRequirementNames=`，只列失败 requirement 名称。

本轮采用方案 B。它不改变门禁结果，只增加稳定摘要字段。

## 完成项

`scripts/test/verify-release-readiness.ps1`

- 从 `$failedRequirements` 中提取等号前的 requirement 名称。
- 新增 metadata 字段：
  - `failedRequirementNames=<none>` 成功路径
  - `failedRequirementNames=name1, name2` 失败路径

`scripts/test/verify-release-scripts.ps1`

- 增加 `failedRequirementNames=` 及提取逻辑的源码结构回归断言。
