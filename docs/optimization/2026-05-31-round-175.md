# 第 175 轮：今日队列不应丢失可回放的 legacy log 卡片

## 审查证据

- `core/database/src/main/java/com/zzz/androidvocab/core/database/OfflineReviewRepository.kt`
  - `repairMissingCardsFromLogs()` 之前只会批量修复 `logs.all { it.hasCardSnapshot() }` 的缺卡。
  - 这让缺失 `review_cards` 的 legacy log 卡片即使可以通过 scheduler 回放，也不会进入 `todayQueue`。
- 同文件的 `replayLogsToCard(...)`
  - 对没有快照的 log 已经支持走 `scheduler.schedule(..., enableFuzzing = false)` 回放。
  - `getQueueItem()` / `submitFeedback()` 也已经依赖这条能力修复 legacy log 缓存。
- `core/database/src/test/java/com/zzz/androidvocab/core/database/OfflineReviewRepositoryTest.kt`
  - 之前只锁定了“scheduler 失败时 legacy log 不会被修”。
  - 没有锁定“scheduler 正常时，legacy log 缺卡应能回到今日队列”。

结论：当前实现让 legacy log 卡片在详情页/反馈路径可恢复，但在今日队列路径会被直接漏掉，行为不一致。

## 方案

- 方案 A：继续只修 snapshot log。
  - 优点：实现简单。
  - 缺点：legacy log 卡片会继续从今日队列消失，和已有单卡修复能力不一致。
- 方案 B：今日队列批量修复也尝试回放 legacy log；若某张卡回放失败，只跳过该卡，不让整条队列流失败。
  - 优点：复用现有回放能力，行为一致，风险可控。
  - 缺点：缺卡扫描时会多做 scheduler 回放。

采用方案 B。

## 修改

- `core/database/src/main/java/com/zzz/androidvocab/core/database/OfflineReviewRepository.kt`
  - `repairMissingCardsFromLogs()` 不再只过滤 snapshot log。
  - 改为对每组缺卡日志都尝试 `replayLogsToCard(...)`。
  - 单卡回放失败时：
    - `CancellationException` 继续抛出
    - 其它异常只跳过该卡，不让整个 `todayQueue` 失败
  - 返回值改为实际修复成功的卡片数量。
- `core/database/src/test/java/com/zzz/androidvocab/core/database/OfflineReviewRepositoryTest.kt`
  - 旧测试重命名为 `todayQueueSkipsLegacyLogRepairWhenReplayFails()`，明确只验证失败降级。
  - 新增 `todayQueueRepairsLegacyLogsWhenSchedulerCanReplayThem()`，锁定正常 scheduler 下 legacy log 缺卡会被修回，并重新出现在今日 due 队列。
