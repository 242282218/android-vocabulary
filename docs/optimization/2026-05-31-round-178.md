# 第 178 轮：数据维护补充快照时间线异常检测

## 审查证据

- `core/database/src/main/java/com/zzz/androidvocab/core/database/OfflineReviewRepository.kt`
  - 上一轮已在提交路径阻止新的乱序 `reviewedAt` 写入。
  - 但 `inspectReviewDataIntegrity()` 还看不到历史库里已经存在的快照时间线异常。
- 同文件 `replayLogsToCard(...)`
  - 对 `hasCardSnapshot()` 的日志会按 `reviewedAt ASC, id ASC` 直接应用 `stateAfter/dueAtAfter/...`。
  - 如果历史上发生过“先写晚日志、后写早日志”，排序后的第一条快照就可能带着 `scheduledDaysBefore=3` 这类不可能属于首条日志的前态。
- `feature/settings/src/main/java/com/zzz/androidvocab/feature/settings/SettingsViewModel.kt`
  - 数据维护文案目前只能区分缺失缓存、不一致、旧日志、孤儿日志和日统计缓存问题。
  - 无法把“日志快照链条本身异常”单独暴露给用户人工处理。

结论：提交路径已经加了新防线，但历史异常数据仍然会被“修完缓存后看起来正常”掩盖，需要单独进入 integrity report。

## 方案

- 方案 A：把时间线异常继续归入 `legacyLogCardCount`。
  - 优点：不扩模型。
  - 缺点：混淆“旧格式日志”和“快照链条异常”两种完全不同的根因，后续修复策略无法区分。
- 方案 B：新增独立的 `timelineConflictCardCount`，作为需人工确认的问题。
  - 优点：语义清晰，设置页与导出都能精确表达，方便后续继续补专门修复能力。
  - 缺点：需要同步 model、inspect、设置页文案、导出 JSON 和测试。

采用方案 B。

## 修改

- `core/model/src/main/java/com/zzz/androidvocab/core/model/ReviewModels.kt`
  - 为 `ReviewDataIntegrityReport` 新增 `timelineConflictCardCount`。
  - `manualReviewIssueCount` 现在会把时间线异常一起计入。
- `core/database/src/main/java/com/zzz/androidvocab/core/database/OfflineReviewRepository.kt`
  - 新增 `hasSnapshotTimelineConflict(...)`。
  - 对所有非 legacy 且具备完整快照的日志，按时间顺序验证每条日志的前态是否还能和当前回放卡片对上：
    - `scheduledDaysBefore`
    - `difficultyBefore`
    - `stabilityBefore`
    - `elapsedDays`
  - 如果任一条对不上，则记为 `timelineConflictCardCount += 1`。
  - 这类问题只算“需人工确认”，不计入 `repairableIssueCount`。
  - `replayLogsToCard(...)` 的基卡构造提炼为类内 `baseCardForReplay(...)`，避免重复。
- `feature/settings/src/main/java/com/zzz/androidvocab/feature/settings/SettingsViewModel.kt`
  - 仅当 `timelineConflictCardCount > 0` 时，在数据维护结果文案末尾追加 `时间线异常 X`。
  - 无该问题时保留原有文案，避免无意义回归。
- `core/database/src/main/java/com/zzz/androidvocab/core/database/AndroidExportRepository.kt`
  - 导出的 `dataIntegrity` JSON 新增 `timelineConflictCardCount`。
