# 第 183 轮：为复习提交补卡片版本校验，拦截过期旧卡重复提交

## 审查证据

- `feature/review/src/main/java/com/zzz/androidvocab/feature/review/ReviewViewModel.kt`
  - UI 已有 `isSubmitting` 和 `submittedCardId` 防重入。
  - 这只能挡住当前 ViewModel 内的重复点击，挡不住过期旧卡从其他入口、恢复流程或未来多消费者路径再次提交。
- `core/domain/src/main/java/com/zzz/androidvocab/core/domain/SubmitReviewFeedbackUseCase.kt`
  - 提交仓库时之前只传 `cardId`、`reviewedAt`、`rating`、`durationMs`、`targetRetention`。
  - 没有携带“用户看到的卡片版本”。
- `core/database/src/main/java/com/zzz/androidvocab/core/database/OfflineReviewRepository.kt`
  - 仓库层之前只校验：
    - 时间不能早于 `lastReviewAt`
    - 重复同一 `reviewedAt` 依赖 `ReviewLog.id` 唯一约束回滚
  - 如果旧 UI 带着同一 `cardId` 再次提交，只要 `reviewedAt` 不同，就会被当成合法第二次复习。

结论：当前缺的是仓库层 optimistic concurrency 防线。仅靠 UI 防重入不足以保护 `ReviewLog -> ReviewCard -> daily_stats` 链路。

## 方案

- 方案 A：提交时带 `ReviewCard.updatedAt` 作为版本令牌。
  - 优点：语义直观。
  - 缺点：新卡没有真实 `ReviewCard` 行时，`updatedAt` 是读取时临时拼出来的，不稳定，会误伤首提交流程。
- 方案 B：提交时带 `lastReviewAt + reviewCount` 作为卡片版本快照。
  - 优点：新卡稳定是 `null + 0`，已学卡每次成功提交都会变化，能准确拦截旧卡重复提交。
  - 缺点：需要多传两个字段，但仍是小改。

采用方案 B。
