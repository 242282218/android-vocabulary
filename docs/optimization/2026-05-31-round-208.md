# 第 208 轮：补齐 pending ReviewLog 的真实链路导出测试

## 审查证据

- `core/database/src/test/java/com/zzz/androidvocab/core/database/AndroidExportRepositoryTest.kt`
  - 上一轮已补 fake `ReviewRepository.report` 的导出契约测试。
  - 仍有缺口：它只能证明 JSON 序列化契约，不足以证明真实 `OfflineReviewRepository.inspectReviewDataIntegrity()` 产出的 pending/legacy 语义会被导出层原样保留。
- `core/database/src/test/java/com/zzz/androidvocab/core/database/OfflineReviewRepositoryTest.kt`
  - 已有 `inspectAndRepairKeepPendingLogsAsManualIssues()`，证明真实仓库层会把 pending 风格日志归类为：
    - `missingCacheCount = 1`
    - `legacyLogCardCount = 1`
    - `manualReviewIssueCount = 1`
    - `repairableIssueCount = 0`
- `core/database/src/main/java/com/zzz/androidvocab/core/database/ExportDao.kt`
  - `reviewLogs()` 从 `valid_review_logs` 导出。
  - 这意味着还需要一条测试同时证明：
    1. pending log 本身会被导出
    2. 真实完整性诊断也会一起导出且不漂移

## 方案

- 方案 A：继续只用 fake report 补更多字段断言
  - 优点：最小、稳定
  - 缺点：不能证明真实仓库和导出层之间的衔接
- 方案 B：在导出测试中直接插入真实 pending 风格日志，用真实 `OfflineReviewRepository` 做完整性检查，再导出 JSON
  - 优点：补齐端到端证据，覆盖真实 DB 行、完整性检查和导出结果
  - 缺点：比 fake 测试稍长

采用方案 B。

## 修改

- 修改 `core/database/src/test/java/com/zzz/androidvocab/core/database/AndroidExportRepositoryTest.kt`
  - 保留上一轮的 fake 契约测试 `exportUserDataKeepsPendingLogIntegrityClassification()`
  - 新增真实链路测试 `exportUserDataReportsPendingLogIntegrityFromRealRepository()`
  - 测试步骤：
    1. 插入一个有 membership、无 `ReviewCard`、快照字段全空的 pending `ReviewLog`
    2. 先把该日 `DailyStats` 从日志回填，避免把焦点污染到 `missingDailyStatsCount`
    3. 用真实 `OfflineReviewRepository.inspectReviewDataIntegrity()`
    4. 通过 `AndroidExportRepository.exportUserData()` 导出 JSON
  - 断言：
    - `reviewCards` 为空
    - `reviewLogs` 仅导出这条 pending log
    - 导出日志的 `algorithmVersion` 仍为 `"<pending>"`
    - `dataIntegrity` 中：
      - `missingCacheCount = 1`
      - `legacyLogCardCount = 1`
      - `repairableIssueCount = 0`
      - `manualReviewIssueCount = 1`
      - `issueCount = 1`
