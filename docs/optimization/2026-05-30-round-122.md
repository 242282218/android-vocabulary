# 第 122 轮：Today 启动批量修复跳过 legacy 日志

## 审查证据

- `OfflineReviewRepository.repairReviewDataCache()` 已按第 21 轮设计，只批量修复所有日志都带完整 after snapshot 的卡片。
- `inspectReviewDataIntegrity()` 会把缺少完整 snapshot 的 legacy 日志计入 `legacyLogCardCount` 和 `manualReviewIssueCount`，不计入可自动修复项。
- 但 `observeTodayQueue()` 的 `onStart` 会调用 `repairMissingCardsFromLogs()`，旧实现会扫描所有缺失 `ReviewCard` 的日志并重放；遇到 legacy 日志时会用当前 scheduler 自动重建卡片，绕过设置页“需人工确认”的语义，也可能在 scheduler 异常时影响 Today 队列加载。

## 方案

- 方案 A：保持启动批量修复覆盖 legacy。兼容性强，但会静默改写无法精确恢复的历史状态，和维护入口的人工确认语义冲突。
- 方案 B：启动批量修复只处理完整 snapshot 日志；legacy 仍可通过 `replayLogs()` 或单卡读取保留兼容 fallback。范围小，和现有审计/修复设计一致。
- 方案 C：新增独立“按当前算法重排 legacy 日志”入口。语义最清楚，但需要 UI、文案、风险提示和更多测试，本轮不做。

采用方案 B。

## 修改

- `core/database/src/main/java/com/zzz/androidvocab/core/database/OfflineReviewRepository.kt`
  - `repairMissingCardsFromLogs()` 先按 `cardId` 分组，再只保留 `logs.all { it.hasCardSnapshot() }` 的分组。
- `core/database/src/test/java/com/zzz/androidvocab/core/database/OfflineReviewRepositoryTest.kt`
  - 新增 `todayQueueDoesNotBatchRepairLegacyLogsWithoutSnapshots`。
  - 使用 `FailingScheduler` 验证 Today 启动不会为 legacy 日志调用 scheduler，也不会写入 `ReviewCard`。
