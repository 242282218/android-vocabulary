# 2026-05-18 持续优化第 11 轮

## 当前状态判断

项目已经从早期设想的 WebView MVP 演进为原生 Android 实现：Kotlin + Jetpack Compose + Room + DataStore + WorkManager + FSRS。当前主流程已经具备离线词库、ReviewLog、统计、提醒、导出、APK/AAB 构建和基础 smoke。继续接近可投入使用，最值得补的是发布链路的可信度和设置页权限闭环。

本轮检查后确认两个实际差距：

- 设置页能提示通知权限缺失，但用户缺少直接进入系统通知设置的路径。
- release / smoke 脚本重复处理 JDK、SDK、adb、apksigner、签名环境变量，后续维护容易出现不一致。
- AAB 验签不能只看 `jarsigner` 退出码；未签名包在部分输出形态下可能造成误判，发布脚本必须基于输出文本做明确判断。

## 对标项目可借鉴点

- Android 官方通知权限文档明确：Android 13+ 的通知依赖 `POST_NOTIFICATIONS` 运行时权限，用户拒绝或在系统设置关闭后，普通通知不能显示。本项目的提醒开关必须把系统权限状态展示给用户。
- Android 官方架构文档强调分层和单一事实来源。脚本侧也应遵循同样原则，把 Android 环境发现抽为共享 helper，而不是每个脚本各写一份。
- Android App Bundle 官方文档建议用 bundletool 模拟 Google Play 的拆包和设备安装。当前 AAB 只完成构建与签名校验，下一步应做安装级验证。
- AnkiDroid 这类成熟 SRS Android 项目有长期发布、签名、许可证和多渠道分发实践；本项目当前仍处在本地 release 链路补齐阶段，必须先把可重复验证做扎实。
- FSRS 以 difficulty、stability、retrievability 为核心变量；本项目已保留这些字段，后续优化重点应继续围绕日志可重放和统计可解释性，而不是堆叠临时指标。

## 差距清单（按 P0/P1/P2/P3）

### P0

- 暂无新增 P0。publish-safe 词库校验、静态检查、单元测试和 debug 构建仍能通过。

### P1

- 通知权限缺失时缺少一键修复路径。影响提醒功能可用性；根因是设置页只展示错误，不提供系统设置入口；建议使用 `ACTION_APP_NOTIFICATION_SETTINGS` 打开当前 App 的通知设置；收益是用户能直接恢复提醒；风险低，主要是不同系统 ROM 入口表现略有差异。
- AAB 签名验证存在误报风险。影响发布可信度；根因是 `jarsigner` 输出语义比退出码更细，未签名和缺 manifest 场景不能只依赖 exit code；建议强制英文输出并同时检查 `jar verified`、排除 `jar unsigned` 和 `no manifest`；收益是未签名 AAB 不会被误报为 verified；风险低。

### P2

- Android 环境发现逻辑重复。影响维护性；根因是 release、bundle、smoke、local verify 脚本分别处理 JDK/SDK/工具路径；建议抽到 `scripts/lib/android-env.ps1`；收益是后续改工具路径或签名检查只改一处；风险中低，脚本入口需要验证。
- 发布文档对 `-AllowUnsigned` 和 AAB 验签语义还不够明确。影响交付沟通；建议补充“只做编译链路验证，不代表可上传/可安装”的说明；收益是降低误分发风险；风险低。

### P3

- AAB 还未通过 bundletool 转 APK Set 并安装到设备。增强发布可信度；建议下一轮新增独立 smoke 脚本；收益高，但需要 bundletool 和在线设备。

## 本轮风险

- `ACTION_APP_NOTIFICATION_SETTINGS` 是系统标准入口，但不同 Android ROM 可能展示不同层级；已保留文案提示，即使跳转表现不同也不影响主流程。
- 公共 helper 改动影响多个脚本入口；已用 local verify、release APK、release AAB 和 smoke list devices 覆盖主要路径。
- 临时测试 keystore 位于 `build/test-signing/`，只用于验证脚本行为，不能作为正式发布密钥。
