# 第 215 轮：release readiness 的 blockerActionSummary 改成依赖感知顺序

## 审查证据

- `scripts/test/verify-release-readiness.ps1`
  - `blockerActionSummaryItems` 之前是按失败 requirement 逐项平铺。
  - 当 `releaseArtifacts` 本身失败时，脚本仍会同时建议：
    - 立刻重跑 `smoke-release-apk.ps1`
    - 立刻重跑 `verify-device.ps1`
    - 立刻补 `smoke-release-bundle-run.txt`
- `docs/release.md`
  - 明确要求失败时优先按 `blockerActionSummary` 的顺序处理，而不是直接从长串 `failureMessage` 排查。

结论：原先的 action summary 没有体现证据链依赖顺序。上游 release artifacts 未就绪时，下游 smoke / device evidence 的建议会误导用户先跑错步骤。

## 方案

- 方案 A：保持现状，只在文档里解释先后依赖
  - 优点：改动最小
  - 缺点：脚本本身仍给出误导性动作顺序
- 方案 B：在 readiness 脚本里生成依赖感知的 action summary
  - 优点：脚本输出本身就能指导正确顺序
  - 缺点：需要补一条脚本回归测试

采用方案 B。

## 修改

- 修改 `scripts/test/verify-release-readiness.ps1`
  - 新增 `Get-DependentRemediationText`
  - 当 `releaseArtifacts` 未通过时：
    - APK smoke action 变成 `after release artifacts pass, ...`
    - device verification action 变成 `after release artifacts pass, ...`
  - 当 `deviceAabVerification` 未通过时：
    - bundle smoke archive action 变成 `after verify-device.ps1 passes, ...`
- 修改 `scripts/test/verify-release-scripts.ps1`
  - 新增组合失败场景回归：
    - release artifacts 失败
    - APK smoke 失败
    - device verification 失败
    - bundle smoke archive 失败
  - 断言 `blockerActionSummary` 现在按依赖顺序输出，不再把下游动作误写成第一步
