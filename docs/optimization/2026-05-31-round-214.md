# 第 214 轮：repairReviewDataCache 现在能修 malformed 当前 ReviewCard.id

## 审查证据

- `core/database/src/main/java/com/zzz/androidvocab/core/database/OfflineReviewRepository.kt`
  - `inspectReviewDataIntegrityInTransaction()` 之前用：
    - `targetCardId = current?.id ?: canonicalCardId(key)`
  - `repairReviewDataCacheInTransaction()` 也同样把 replay 目标 id 绑定到当前缓存 id。
- `core/database/src/main/java/com/zzz/androidvocab/core/database/OfflineReviewRepository.kt`
  - `ReviewCard.differsFrom()` 不比较 `id`，只比较调度状态字段。

结论：如果数据库里已经有一条 malformed 的当前 `review_card`，并且它的调度状态与日志 replay 结果一致，那么：

- integrity 不会把它记成 `inconsistentCacheCount`
- repair 也不会把它修回 canonical `card|book|word`

也就是说，这类缓存污染只能靠 `getQueueItem()` / Today 队列读路径顺手修，仓库层的完整性检查与批量 repair 仍然看不见。

## 方案

- 方案 A：把 malformed 当前 `ReviewCard.id` 记成 manual issue，不在 repair 中处理
  - 优点：实现更小
  - 缺点：这是可修复的缓存问题，不应降级成人工问题
- 方案 B：把 malformed 当前 `ReviewCard.id` 视为 repairable cache issue
  - 优点：与“当前卡片缓存必须 canonical”一致；repair 可直接修复，不依赖 UI 读取链路
  - 缺点：要同时补 integrity 和 repair 两处逻辑

采用方案 B。

## 修改

- 修改 `core/database/src/main/java/com/zzz/androidvocab/core/database/OfflineReviewRepository.kt`
  - integrity 检查改为显式识别 `current.id != canonicalCardId(key)`
  - 这类问题计入 `inconsistentCacheCount` 与 `repairableIssueCount`
  - repair 先把 malformed 当前卡片直接 canonicalize，再决定是否还需要 replay 覆盖状态
  - replay / timeline 比较统一改为使用 canonical `targetCardId`
- 修改 `core/database/src/test/java/com/zzz/androidvocab/core/database/OfflineReviewRepositoryTest.kt`
  - 新增 `inspectAndRepairTreatMalformedCurrentCardIdAsRepairableCacheIssue()`
  - 证明：
    - integrity 现在能发现这类缓存污染
    - repair 能直接修成 canonical card
    - 不会把它误报成 manual issue
