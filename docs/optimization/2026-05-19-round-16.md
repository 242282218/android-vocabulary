# 2026-05-19 持续优化第 16 轮

## 当前状态判断

第 15 轮验证了 `ReviewCard` 缓存缺失时可以通过 `ReviewLog` 重建状态，但进一步检查发现，现有日志字段无法做到真正的历史精确恢复。`ReviewLog` 只有 `scheduledDaysAfter`、`difficultyAfter`、`stabilityAfter`、`retrievabilityAfter`，缺少 `stateAfter` 和 `dueAtAfter`。这意味着恢复时只能重新跑当前 scheduler，算法升级后可能得到和当时不同的卡片状态。

## 对标项目可借鉴点

- SRS 项目需要区分“历史快照恢复”和“按新算法重排”。前者用于数据修复和导出导入，后者用于算法迁移。
- Review history 应保留足够的 after snapshot，让卡片缓存不是唯一事实来源。
- Room schema 变更必须提供显式 migration，并保留旧数据兼容路径。

参考：

- https://developer.android.com/training/data-storage/room/migrating-db-versions
- https://github.com/open-spaced-repetition/free-spaced-repetition-scheduler

## 差距清单（按 P0/P1/P2/P3）

### P0

- 暂无新增 P0，完整本地验证通过。

### P1

- `ReviewLog` 缺少 `stateAfter` 和 `dueAtAfter`，无法精确恢复卡片快照。影响算法升级、数据修复和导出导入可信度；根因是日志只记录了部分调度结果；建议升级数据库到 v3，给新日志写入完整 after 快照，旧日志保持 nullable 并 fallback 到 scheduler；收益是新数据具备历史精确恢复能力；风险中等，涉及 schema 和迁移。

### P2

- 导出 JSON 中缺少新的 after 快照字段。影响未来数据迁移；建议同步导出；收益是备份更完整；风险低。

### P3

- 还没有单独暴露“按最新 scheduler 重排”的 use case。当前先保留旧日志 fallback，后续需要产品语义时再加。

## 本轮要做的优化项

1. `ReviewLog` / `ReviewLogEntity` 增加 `stateAfter` 和 `dueAtAfter`。
2. 数据库版本升级到 3，并新增 `MIGRATION_2_3`。
3. `submitFeedback` 写日志时保存 `nextCard.state` 与 `nextCard.dueAt`。
4. `replayLogs` 对新日志使用 after snapshot 恢复；旧日志缺字段时 fallback 到 scheduler。
5. 导出 JSON 增加新字段。
6. 补单测和迁移测试编译验证。

## 本轮风险

- 旧日志没有 `stateAfter` / `dueAtAfter`，只能继续 fallback 到 scheduler；这是兼容策略，不是历史精确恢复。
- 新字段为 nullable，迁移不会破坏现有安装数据。
- 真正执行 migration instrumentation test 仍需要设备或模拟器；本轮完成了 androidTest 编译验证。

## 下一轮建议

1. 把 androidTest APK 编译纳入本地验证和 CI，避免迁移测试或布局 smoke 编译失败漏掉。
2. 后续如需算法升级，新增独立“按最新 scheduler 重排”use case，不复用历史精确恢复路径。
