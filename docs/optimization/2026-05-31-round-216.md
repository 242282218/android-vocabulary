# 第 216 轮：GitHub Actions release evidence 绑定当前仓库

## 审查证据

- `scripts/test/write-github-actions-evidence.ps1`
  - 之前只写 `workflow`、`conclusion`、`commitSha`、`runId`、`runAttempt`、`runUrl`、`checks`。
  - `runUrl` 虽然看起来指向当前仓库，但 readiness 侧没有独立读取 `serverUrl` 和 `repository`。
- `scripts/test/verify-release-readiness.ps1`
  - 原先主要校验 `commitSha`、`checks`、`runId`、`runAttempt`、`runUrl` 非空与格式。
  - 如果有人把别的仓库成功运行的 URL 拼成相同模式，现有证据约束不够直接。
- `scripts/test/verify-release-scripts.ps1`
  - 已有正向和缺字段回归，但还需要覆盖“仓库名不匹配当前 HEAD 所在仓库”的失败场景。

结论：只靠 `runUrl` 和 `commitSha` 不够严格。release readiness 应显式绑定 `https://github.com/<owner>/<repo>`，把 workflow 运行来源收紧到当前仓库。

## 方案

- 方案 A：继续只校验 `runUrl`
  - 优点：改动最小
  - 缺点：约束隐含在 URL 字符串里，可读性和错误定位都差
- 方案 B：在 evidence 中显式写入 `serverUrl`、`repository`，readiness 逐项校验并让回归覆盖跨仓库伪造场景
  - 优点：证据格式更明确，失败原因可直接落到字段
  - 缺点：需要同步 writer、readiness、回归测试和发布文档

采用方案 B。

## 修改

- 修改 `scripts/test/write-github-actions-evidence.ps1`
  - 新增输出 `serverUrl=$env:GITHUB_SERVER_URL`
  - 新增输出 `repository=$env:GITHUB_REPOSITORY`
  - `runUrl` 由 `serverUrl/repository/runId` 组合生成
- 修改 `scripts/test/verify-release-readiness.ps1`
  - `Test-GitHubActionsRunUrl` 改为同时接收 `RunId`、`ServerUrl`、`Repository`
  - 要求 `serverUrl`、`repository`、`runId` 非空，且 `repository` 必须匹配 `owner/repo`
  - 要求 `serverUrl=https://github.com`
  - 要求 `runUrl == "$serverUrl/$repository/actions/runs/$runId"`
  - readiness metadata 和 failure evidence 新增 `githubActionsServerUrl`、`githubActionsRepository`
- 修改 `scripts/test/verify-release-scripts.ps1`
  - 更新 writer 结构断言和正向 fixture
  - 新增跨仓库失败场景：`repository=zzz/other-repo` 时必须阻断 `githubActionsEvidence`
- 修改 `docs/release.md`
  - 同步 evidence 示例格式和新校验约束
