# 第 172 轮：Settings 需要区分“缺权限”和“系统通知已关闭”

## 审查证据

- `feature/settings/src/main/java/com/zzz/androidvocab/feature/settings/SettingsRoute.kt`
  - 提醒开关之前只依赖 `hasNotificationPermission()` 这个单一布尔值。
  - 该判断只覆盖 Android 13+ 的 `POST_NOTIFICATIONS` 运行时权限，没有覆盖应用级通知总开关。
- 同文件 `ReminderCard(...)`
  - UI 只有“系统通知权限未开启，每日提醒不会显示。”这一类恢复提示。
  - 用户在系统里关闭整个应用通知后，Settings 没有独立的暂停说明，容易误以为提醒仍会正常工作。
- `app/src/androidTest/java/com/zzz/androidvocab/ScreenLayoutSmokeTest.kt`
  - 之前只覆盖了“权限缺失”的提醒提示，没有覆盖“系统通知已关闭”的状态。

结论：提醒正确性已经在 `app/worker` 层收敛，但 Settings 体验层仍把两类不可用状态混在一起，缺少对系统通知关闭场景的明确反馈。

## 方案

- 方案 A：继续沿用一个权限布尔值，只调整文案。
  - 优点：改动最少。
  - 缺点：无法正确区分“该弹权限请求”和“只能引导去系统设置恢复通知”两条路径。
- 方案 B：在 `feature/settings` 内引入独立的提醒通知状态枚举，Route 根据状态决定开关行为，Card 根据状态展示不同恢复提示。
  - 优点：不跨模块改架构，只在 Settings 内补齐状态表达，行为和 UI 都能对齐。
  - 缺点：会增加一个小的 UI 状态模型和少量测试。

采用方案 B。

## 修改

- `feature/settings/src/main/java/com/zzz/androidvocab/feature/settings/ReminderNotificationState.kt`
  - 新增 `ReminderNotificationState`：
    - `Granted`
    - `MissingRuntimePermission`
    - `DisabledInSystem`
  - 新增 `resolveReminderNotificationState(...)` 纯函数，优先判断运行时权限，再判断系统通知开关。
- `feature/settings/src/main/java/com/zzz/androidvocab/feature/settings/SettingsRoute.kt`
  - `SettingsRoute` 本地状态改为 `reminderNotificationState`。
  - `ON_RESUME`、权限请求回调、提醒开关点击都统一重新读取通知状态。
  - 仅在 `MissingRuntimePermission` 时才拉起 `POST_NOTIFICATIONS` 请求；系统通知关闭时允许保留用户“想开启提醒”的意图，并在 UI 中显示暂停说明。
  - `ReminderCard` 新增系统通知关闭文案：
    - `系统通知已关闭，每日提醒已暂停；重新开启后会自动恢复。`
- `feature/settings/src/test/java/com/zzz/androidvocab/feature/settings/ReminderNotificationStateTest.kt`
  - 补三态解析的 JVM 单测，锁定优先级和 Android 13 前后行为。
- `app/src/androidTest/java/com/zzz/androidvocab/ScreenLayoutSmokeTest.kt`
  - 把原提醒 smoke case 切到 `MissingRuntimePermission`。
  - 新增 `settingsScreenExplainsPausedReminderWhenSystemNotificationsAreDisabled()`，锁定系统通知关闭时的提示文案和入口按钮。
