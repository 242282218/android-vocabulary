# 2026-05-19 持续优化第 14 轮

## 当前状态判断

项目核心数据链路是 `ReviewLog` 先写入，再更新 `ReviewCard` 和 `DailyStats`。这个方向正确，但重复提交同一次复习反馈是实际使用中会发生的边界：UI 已有防重复点击保护，但进程卡顿、恢复、或未来多入口提交时仍可能打到数据库唯一约束。之前依赖 Room 约束异常自然回滚，但异常会原样冒泡，UI 文案不可控，且没有测试证明事务不会污染卡片和统计。

## 对标项目可借鉴点

- Android Room 支持事务边界；写入复习日志、更新卡片、刷新统计必须在同一事务内，任何一步失败都不能留下半状态。
- Android 官方架构建议 repository 作为数据层边界，对外暴露稳定错误语义，而不是把数据库底层异常泄露给 UI。
- 成熟 SRS 项目的复习历史是事实来源；重复日志不能被“覆盖”或静默吞掉，否则统计和调度都会失真。

参考：

- https://developer.android.com/reference/androidx/room/Transaction
- https://developer.android.com/topic/architecture/data-layer
- https://github.com/ankidroid/Anki-Android

## 差距清单（按 P0/P1/P2/P3）

### P0

- 暂无新增 P0。完整本地验证通过。

### P1

- 重复复习日志冲突缺少明确错误处理和回滚测试。影响数据正确性和用户错误反馈；根因是 `insertLog` 使用 `OnConflictStrategy.ABORT`，但 repository 未把约束异常转换为领域错误，也没有断言 `ReviewCard` / `DailyStats` 不被二次更新；建议捕获 `SQLiteConstraintException` 并转换为 `AppError.DatabaseWriteFailed`，同时补事务回滚测试；收益是重复提交不会污染学习状态，UI 能展示稳定文案；风险低。

### P2

- `scheduleOrThrow` 会捕获所有 `Exception`，理论上可能吞掉协程取消。影响可维护性；建议显式重抛 `CancellationException`；收益是符合 coroutine 约定；风险低。

### P3

- 后续还可以把数据库写入异常细分成重复提交、记录不存在、未知写入失败，但当前不必过度拆分。

## 本轮要做的优化项

1. `submitFeedback` 捕获重复日志约束异常，转换为稳定的 `AppError.DatabaseWriteFailed`。
2. 保持 Room transaction 的原子性，失败时不更新 `ReviewCard` 和 `DailyStats`。
3. `scheduleOrThrow` 显式重抛 `CancellationException`。
4. 补数据库层回归测试。

## 具体修改方案

- `core/database/src/main/java/com/zzz/androidvocab/core/database/OfflineReviewRepository.kt`
  - `submitFeedback` 外层增加错误转换：
    - `CancellationException` 原样抛出。
    - `AppException` 原样抛出。
    - `SQLiteConstraintException` 转换为 `AppError.DatabaseWriteFailed("本次反馈已保存，请勿重复提交")`。
    - 其他异常转换为 `DatabaseWriteFailed`。
  - `scheduleOrThrow` 显式重抛 `CancellationException`。
- `core/database/src/test/java/com/zzz/androidvocab/core/database/OfflineReviewRepositoryTest.kt`
  - 新增 `duplicateReviewLogRollsBackCardAndStatsUpdates`。
  - 第一次提交 Good 后记录当前卡片。
  - 第二次用相同 `reviewedAt` 提交 Hard，触发相同 log id。
  - 断言异常类型为 `DatabaseWriteFailed`。
  - 断言日志仍只有 Good，卡片字段未变化，统计仍只有 1 次完成和 1 次新学。
