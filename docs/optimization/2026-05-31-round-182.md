# 第 182 轮：锁定复习提交的持久化顺序边界

## 审查证据

- `AGENTS.md`
  - 项目规则要求 `ReviewLog` 是事实来源，复习链路应先落日志，再推进 `ReviewCard` 和缓存。
- `docs/plans/2026-05-16-english-vocabulary-app-development-design.md`
  - `10.3 复习事务` 已明确：
    1. 读取当前 `ReviewCard`
    2. 调用 `ReviewScheduler.schedule`
    3. 插入不可变 `ReviewLog`
    4. 更新 `ReviewCard`
  - 这里实际强调的是持久化边界，而不是要求把 FSRS 计算推迟到日志写入之后。
- `core/database/src/main/java/com/zzz/androidvocab/core/database/OfflineReviewRepository.kt`
  - `submitFeedback()` 之前把“计算 FSRS / 组装日志 / 插入日志 / 更新卡片”全部揉在一个代码块里。
  - 真实写库顺序没有错，但结构不够显式，容易让后续维护者误改。
- `core/database/src/test/java/com/zzz/androidvocab/core/database/OfflineReviewRepositoryStatsAndRollbackTest.kt`
  - 已有回滚测试覆盖 scheduler 失败、重复日志冲突、卡片写失败。
  - 缺口：没有测试直接锁定成功路径上的持久化调用顺序。

结论：当前根因不是 schema 错，也不是事务顺序错，而是提交链路的“准备阶段”和“持久化阶段”没有被清晰分开，导致项目规则只能靠人工阅读理解，缺少结构化防线。

## 方案

- 方案 A：保持现有 schema 和事务语义，把 `submitFeedback()` 拆成“准备复习结果”和“按 `insertLog -> upsertCard -> refreshDailyStats` 持久化”两段，并补 DAO 调用顺序测试。
  - 优点：外科手术式修改，不动迁移、导出、重放和统计。
  - 缺点：不去重做“原始事件表 + 派生快照”的更大数据模型。
- 方案 B：重做为两张表，先写原始反馈事件，再计算 FSRS，再写派生日志/卡片。
  - 优点：概念最纯。
  - 缺点：需要连带修改 schema、迁移、导出、repair、统计，当前轮次明显过大。
- 方案 C：只补文档，不动代码和测试。
  - 优点：成本最低。
  - 缺点：无法防止未来有人把 `upsertCard` 提前到 `insertLog` 前面。

采用方案 A。

## 修改

- `core/database/src/main/java/com/zzz/androidvocab/core/database/OfflineReviewRepository.kt`
  - 新增 `prepareReviewResult(...)`，把 FSRS 计算和 `ReviewLog` 组装集中到内存准备阶段。
  - `submitFeedback()` 现在显式执行：
    1. 准备 `ReviewResult`
    2. `insertLog`
    3. `upsertCard`
    4. `refreshDailyStats`
- `core/database/src/test/java/com/zzz/androidvocab/core/database/OfflineReviewRepositoryTestSupport.kt`
  - 新增 `RecordingPersistenceOrderReviewDao`，记录 `insertLog` / `upsertCard` 调用顺序。
- `core/database/src/test/java/com/zzz/androidvocab/core/database/OfflineReviewRepositoryStatsAndRollbackTest.kt`
  - 新增 `submitFeedbackPersistsReviewLogBeforeReviewCard()`，直接锁定成功路径的持久化顺序。
