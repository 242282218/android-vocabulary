# 2026-05-19 持续优化第 20 轮

## 当前状态判断

第 19 轮已经让 `getQueueItem` / `submitFeedback` 在 `ReviewCard` 缓存缺失但 `ReviewLog` 存在时自动重建卡片，避免继续反馈时从新卡错误起算。

继续检查 Today 队列入口后发现同源问题仍有残留：`observeNewQueue` 只通过 `review_cards` 判断一个词是否未学。如果某张学过的卡片缓存丢失，但日志还在，它会先出现在新词队列中。即使用户提交反馈时会被第 19 轮逻辑修复，首页仍会展示错误队列，影响每日新词上限和用户对学习进度的信任。

## 对标项目可借鉴点

- 成熟 SRS 实现会避免把有复习历史的卡片重新暴露为新卡；队列生成必须尊重复习日志这个事实来源。
- 离线本地应用常用“读前轻量修复”处理派生缓存缺失：进入核心队列前先恢复必要缓存，再让原查询路径工作。
- SQL 层应有防线：即使修复流程未覆盖到，也不应让已有日志的词进入新词候选。

## 差距清单（按 P0/P1/P2/P3）

### P0

- Today 新词队列可能把有 `ReviewLog` 但缺 `ReviewCard` 的词当新词。影响范围是首页队列、每日新词上限、复习正确性；根因是新词 SQL 只看缓存表；建议队列加载前修复缺失缓存，并在 SQL 层排除已有日志；预期收益是事实来源一致；风险中等，涉及队列 Flow 和 DAO 查询。

### P1

- 缺少批量修复入口。影响范围是大量异常数据恢复；根因是第 19 轮只在单卡读取时修复；建议增加 `getCardIdsMissingCacheFromLogs` 并在 Today 队列加载前批量修复可恢复卡片；收益是用户进入学习台时自动恢复队列；风险低到中。

### P2

- 修复过程目前没有返回给 UI 的可见提示。影响范围是可观测性；建议后续只在调试/维护入口显示，不打扰普通学习流程。

### P3

- 可以为修复数量增加内部日志，但当前项目还没有统一 logger，暂不引入。

## 本轮要做的优化项

1. DAO 增加“有日志但缺缓存”的 cardId 查询。
2. Today 队列加载前自动修复这些缺失卡片。
3. 新词 SQL 显式排除已有 `review_logs` 的词书 membership。
4. 补测试覆盖 Today 队列自动修复与新词排除。

## 具体修改方案

- `core/database/src/main/java/com/zzz/androidvocab/core/database/ReviewDao.kt`
  - 新增 `getCardIdsMissingCacheFromLogs()`：
    - 从 `review_logs` 查找没有对应 `review_cards` 的 cardId。
    - 只修复仍有 `wordbook_memberships` 的卡片，避免已移除词书 membership 的历史日志影响队列。
  - `observeNewQueue()` 增加 `LEFT JOIN review_logs`，并要求 `l.id IS NULL`，防止有日志的词进入新词候选。

- `core/database/src/main/java/com/zzz/androidvocab/core/database/OfflineReviewRepository.kt`
  - `observeTodayQueue()` 改为 Flow 包装：收集前先在事务内执行 `repairMissingCardsFromLogs(now)`，再订阅 due/new 队列。
  - 新增 `repairMissingCardsFromLogs(now)`，复用 `replayLogsToCard` 重建并写回缺失缓存。

- `core/database/src/test/java/com/zzz/androidvocab/core/database/OfflineReviewRepositoryTest.kt`
  - 新增 `todayQueueRepairsMissingReviewCardCacheBeforeLoading`，验证：
    - 学过的卡片缓存缺失后，Today 队列加载前会恢复缓存。
    - 该词不会出现在新词列表。
    - 到期时会出现在复习列表。

## 本轮风险

- Today 队列首次收集时会额外查询缺失缓存列表；正常情况下结果为空，成本很低。
- 如果存在 legacy 日志且 scheduler 未来发生不兼容变化，修复结果仍可能与历史状态不完全一致；新 v3 日志通过快照规避了这个问题。
- 自动修复仍只覆盖有词书 membership 的日志；被词库更新移除的历史日志不会重新变成可学习卡片。

## 下一轮建议

1. 增加数据一致性“审计”能力：不仅修复缺失卡片，也检测 `review_cards` 与最后一条 `review_logs` 快照不一致。
2. 为 `ReviewLog` 和 `ReviewCard` 的一致性增加更直接的 DAO 级测试，覆盖 SQL 查询边界。
3. 有设备后执行 `verify-device.ps1`，确认队列修复不影响真实启动和 Room 查询。
